Scivo is good. Here's how it gets dangerous.

A fresh audit of every API route, library, and schema found 15 specific places where Speed, Quality, or Cost can move materially — plus 3 architectural blockers that have to land before Scivo serves more than one agency. Sequenced below by impact-per-day-of-work, with file-and-line citations so nothing is hand-waved.

Pillar 01 · Speed
~17 min → ~5 min
~17 min / video→~5 min / video

Five sequential loops that should be parallel batches. Webhook callbacks instead of 5-second polling. N+1 query elimination. The wall-clock improvement compounds across 1,000 videos.

Pillar 02 · Quality
5 gates → real, blocking, on every route
vision QA logged→vision QA acted on

Auto-retake exists in one route, missing in the production routes. Reference URL mapping has a bug feeding wrong views to QA. The video gate is currently checking keyframes (placebo). All three are file-line fixes.

Pillar 03 · Cost
$3.70 → $2.40 / video std
$3.70 / 60s · ~$3,700 / mo→$2.40 / 60s · ~$2,400 / mo

Cheapest-provider routing is registered but dead code. FluxAPI ~40% cheaper than current FLUX path. Hypereal flat $0.04/image. Fish Audio 55% cheaper than ElevenLabs. Wiring the registry pays back in week one and unlocks per-stage swaps (Veo for hero shots, Hailuo for cutaways).

Speed winsFive places the pipeline is waiting on itself.

Each one is a measured slowdown — not a "should be faster" hunch. Estimated wall-clock impact is the per-video gain; multiply by your monthly volume for the actual dollar value.

S1

Parallelize the production-path generate routes

Default /api/generate/keyframe, /video, /audio still run shots one-at-a-time via for…of await. Only the standalone /batch route uses parallel runBatch(…, 6). Switch the production routes to the same pattern.
Filessrc/app/api/generate/keyframe/route.ts:73-101 · video/route.ts:63-94 · audio/route.ts:46-58
Impact~6× speedup on "generate scene" actions. 7-shot scene: ~14 min → ~2.5 min on Kling 3.0.
HIGH~2 hrs effort
S2

Replace fixed-interval polling with webhooks + backoff

Kie.ai client polls every 5s with no jitter or backoff. For Veo3 Fast (~60s gen) you waste up to 5s per cycle. The Suno endpoint already accepts a callBackUrl — currently pointed at httpbin.org. Switch to webhooks where supported, exponential backoff (1.5s → 8s) elsewhere.
Filessrc/lib/ai/kie-client.ts:34-35, 590
ImpactFirst-result latency ~30% lower, function compute ~50% lower (matters for Vercel billing).
HIGH~4 hrs effort
S3

Kill the N+1 in generation-tracker

completeGeneration → updateProjectTotals → another findUniqueOrThrow on Generation, then a third query to resolve projectId via Scene/Shot/Character. Multiplied by every generation. Denormalize projectId onto the Generation row.
Filessrc/lib/ai/generation-tracker.ts:351-435
Impact3 DB queries → 1 per generation. At 1,000 videos × 30 gens = 60k saved queries/month.
MID~3 hrs effort
S4

Parallelize character-sheet view generation

The 5 non-front views are still generated sequentially, even though they share one input image and have no inter-view dependency. Wrap in runBatch(tasks, 5).
Filessrc/app/api/generate/character-sheet/route.ts:288-312
ImpactCharacter sheet generation: 5 × 30s = 150s → ~30s.
MID~30 min effort
S5

Hoist next/dynamic imports out of stage components

Three dynamic imports (ModelSwitcher, GenerationProgress, EditablePrompt) are declared inside Client Components and re-execute on every render — measurable scroll-jank source.
Filessrc/app/(dashboard)/projects/[projectId]/keyframes/page.tsx:34-36 & siblings
Impact~10-15% TTI improvement on stage pages.
QUICK~30 min effort

Cost winsFive places we're paying retail.

The provider registry is the highest-leverage piece of architecture in the codebase — and it's currently dead code. Wiring it correctly is the single largest cost win available, and there are four more provider-level swaps that compound on top of it.

C1

Wake up the multi-provider registry · the architecture's biggest unlock

All non-kie-ai providers are hard-flagged isAvailable: false. Routes are hardcoded to kie.ai. The "intelligent provider selection" never actually selects PiAPI, Hypereal, FluxAPI, or Fish Audio — even though research shows FluxAPI 40% cheaper for FLUX Kontext, Hypereal flat $0.04/image, Fish Audio 55% cheaper than ElevenLabs.
Filessrc/lib/ai/cost-data.ts:743-754 · provider-registry.ts:431-806
Impact~$300-500/mo savings at 1,000 videos. Plus opens per-project model overrides as a real product feature.
HIGH~1 day effort
C2

Kill the hardcoded cost tables in generation routes

Hardcoded cost tables in keyframe/video routes duplicate cost-data.ts and are stale: Kling 3.0 listed at $0.10/image (it's a video model), Veo3 fast at $0.15 (cost-data says $0.0375/s). Cost reporting is wrong by 2-4× in places. Use getVideoUnitCost()/getImageUnitCost() uniformly.
Fileskeyframe/route.ts:12-16 · video/route.ts:9-13
ImpactCost reporting becomes truthful. Currently affecting margin decisions silently.
HIGH~1 hr effort
C3

Switch GPT-4o Vision to GPT-4o-mini, or batch via OpenAI Batch API

Every successful keyframe triggers a GPT-4o Vision call (~$0.01-0.02/check, high detail). At 1,000 videos × ~30 keyframes × 2 calls = ~$600/mo on vision alone. Options: GPT-4o-mini (10× cheaper, similar accuracy on this task), or only run when project consistency-score is below a threshold, or use OpenAI's Batch API (50% off).
Filessrc/lib/ai/quality-gates.ts:618-657, 706-805, 861-923
Impact~$300-500/mo savings on vision QA at target scale.
MID~4 hrs effort
C4

Per-view cost rows + failure tracking on character sheets

Character-sheet cost rolls up to one Generation record ($0.17 total). Per-view generations don't get individual rows. Can't detect which view consistently fails, or which model wastes credits. generateForCharacter doesn't failGeneration on partial failures — silent log only. You're billing for failed sheets.
Filecharacter-sheet/route.ts:329-337
ImpactCloses a hidden cost leak. Better data for which view/model needs the next prompt-engineering pass.
MID~3 hrs effort
C5

Cache the speaker → voice → TTS-param map per project

detectSpeakerWithClaude runs a Claude Sonnet call per shot to detect speaker + TTS params. ~30 dialogue shots/video × 1,000 videos = 30k Claude calls (~$30/mo) plus heavy latency in the audio batch. The mapping is deterministic per character — cache it.
Filesrc/app/api/generate/audio/route.ts:128-188
Impact~95% LLM call reduction in the audio stage. Faster audio generation as a side effect.
MID~3 hrs effort
BlockersThree things between us and shipping this to your team.

Performance wins are gravy. These three are different — they're architectural. Without them Scivo can't be exposed beyond a single dev session. They're flagged separately because they need decisions, not just code.

B1

No background queue · no auth · function-scope orphan jobs

Generation work is fire-and-forget inside Next.js serverless routes. When the function recycles (Vercel ~10min limit), in-flight jobs orphan with their Generation row stuck in processing. Zero authentication on every API route — anyone with a project ID can trigger expensive generations.

Fix: Move generation work to a background queue (Inngest, BullMQ + worker, or Vercel Cron + a queue table). Add session auth to every API route. Until both land, Scivo cannot be exposed to your team or to a client.
B2

SQLite + better-sqlite3 will not survive concurrent writes

Schema uses file-based SQLite. With runBatch of 6 concurrent generations all writing Generation rows + incrementing Project.actualCost, you'll hit SQLITE_BUSY lockups at concurrent-user scale. The scripts/restore-seekho-urls.ts file in your repo suggests this has already bitten once.

Fix: Migrate to Postgres (Neon or Supabase). Prisma schema needs only provider = "postgresql" and removal of the better-sqlite3 adapter dance in src/lib/db.ts. ~1 day of work, plus a data migration plan.
B3

No project ownership · no multi-tenancy · global Settings table

The Project model has no userId / teamId / workspaceId. Settings is keyed only by key — meaning if two agencies sign up, they share one set of API keys. There's also no rate limiting anywhere in the codebase.

Fix: Add userId / workspaceId to Project and Settings now (adding it later is a destructive migration). Gate every API route. Add per-workspace rate limits before any second user touches the system.
Three surprisesThings the audit found that nobody was looking for.
Surprise · architectural

The whole multi-provider engine is dead code in production

provider-registry.ts registers 28 providers with rich getRecommended() logic, but no API route ever calls providerRegistry.resolveProvider(). Routes are hardcoded to kie.ai providers (generateImageNanaBananaPro, generateVideoKling3). The "savings vs. competitors" math in the cost-comparison page is showing theoretical numbers nobody is realizing yet. C1 above unlocks this — and it's the single highest-leverage architectural win in the audit.

Surprise · multi-tenancy

The Settings table is global · API keys are shared across all "users"

src/app/api/settings/route.ts:37-58 upserts to a flat Settings table keyed only by key. If a second team signed up tomorrow, they'd literally share API keys with you. The Settings page architecturally cannot support multi-tenancy without a schema change. Solvable, but worth flagging as a gating condition for any external rollout.

Surprise · data fragility

Recovery scripts already exist · the SQLite warning is not theoretical

scripts/restore-seekho-urls.ts is in the repo (untracked), implying production data loss has already happened at least once. Combined with exports/scene1-assembled.mp4 being a real artifact, this codebase has been in patch-and-pray mode that won't survive the next 10× of usage. B2 is the path out.
